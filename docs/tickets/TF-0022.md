## Objetivo

Registro persistente y consultable de cada ejecución relevante (humana o de
agente) asociada a un ticket, para materializar la trazabilidad de `CLAUDE.md`
§28. **Una sola tabla nueva**, con el patrón de persistencia actual (SQLite,
`CREATE TABLE IF NOT EXISTS` dentro de `crear_tablas()`, sin ORM ni migraciones).

La tabla `acciones` es **infraestructura de trazabilidad, no parte del dominio de
tareas/proyectos**.

## Contexto

Promoción de **BL-17** (origen: análisis de arquitectura para agentes,
2026-08-29).

Estado actual: `crear_tablas()` en `src/database.py` crea `proyectos` y `tareas`
(con FK `tareas.proyecto_id → proyectos.id`) y siembra el proyecto `id=0`.
`get_connection()` ejecuta `PRAGMA foreign_keys = ON` (TF-0015). El acceso a datos
sigue el patrón "una conexión por operación" (`DBManager`). No hay ningún registro
de ejecuciones/acciones.

El `ticket` que referenciará `acciones` es un identificador textual `TF-XXXX` del
sistema de tickets de `docs/`, **no** una fila de `tareas` ni de `proyectos`.

## Alcance

- Extender `crear_tablas()` en `src/database.py` con:

  ```sql
  CREATE TABLE IF NOT EXISTS acciones (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket         TEXT,
    actor          TEXT NOT NULL,      -- p. ej. 'humano:pao' | 'agente:documentador'
    tipo           TEXT NOT NULL,      -- p. ej. 'generar_doc_ticket'
    entrada        TEXT,               -- JSON (string)
    resultado      TEXT,               -- JSON (string)
    estado         TEXT NOT NULL,      -- EN_CURSO | COMPLETADA | FALLIDA
    creado_en      TEXT NOT NULL,
    actualizado_en TEXT
  )
  ```

  Sin FK (el `ticket` no referencia `tareas`/`proyectos`). Sin índices (hasta que
  haya volumen real, §30).
- Nuevo `src/repositorios/__init__.py` y `src/repositorios/acciones.py` con
  `RepositorioAcciones`:
  - `registrar(ticket, actor, tipo, entrada) -> int` — crea la fila en `EN_CURSO`
    con `creado_en` = ahora; devuelve el `id`.
  - `marcar(id, estado, resultado=None) -> bool` — actualiza `estado`,
    `resultado` y `actualizado_en`; devuelve `False` si el `id` no existe (mismo
    patrón que `DBManager.marcar_tarea_completada`). Rechaza `estado` fuera del
    conjunto permitido.
  - `obtener(id) -> dict | None`.
  - `listar(ticket=None) -> list[dict]`.
- `entrada` / `resultado`: el repositorio acepta un `dict` (lo serializa con
  `json.dumps`) **o** un `str` ya serializado. **No importa las dataclasses de
  TF-0021** — trabaja con JSON genérico (condición de aprobación).
- Usa `get_connection()` tal cual (respeta `PRAGMA foreign_keys = ON`). Mantiene
  el estilo "una conexión por operación"; **no** introduce sesión / unit-of-work.
- El conjunto de estados `{EN_CURSO, COMPLETADA, FALLIDA}` se define como
  constantes del módulo.

## Criterios de aceptación verificables

1. Tras `DBManager()` / `crear_tablas()`, existe la tabla `acciones` con las

   `creado_en` no nulo y `actualizado_en` nulo.
3. `marcar(id, "COMPLETADA", resultado={...})` actualiza `estado` y `resultado`
   (legible con `json.loads`), fija `actualizado_en` y devuelve `True`; con `id`
   inexistente devuelve `False` y no crea filas.

   escribir.

   `obtener(inexistente)` → `None`.

   cual); round-trip `dict → guardar → obtener → dict` estable.
8. Insertar una acción con un `ticket` arbitrario **no** requiere filas en
   `tareas` / `proyectos` y **no** dispara error de FK.
9. `src/repositorios/acciones.py` no importa Flask ni `app`; `DBManager` no

## Riesgos

- **R1 (medio)** — `test_database.py` tiene helpers que enumeran las tablas
  esperadas; añadir `acciones` puede requerir extender un helper compartido.
  *Mitigación:* añadir casos nuevos, no alterar los existentes; si un helper es
  rígido, extenderlo de forma **aditiva**.
- **R2 (bajo)** — Formato de fecha: usar el mismo que `crear_tarea`
  (`"%Y-%m-%d %H:%M:%S"`) o ISO 8601 — decidir en el checkpoint; cubrir con test
  de formato.
- **R3 (bajo)** — Semántica de `estado`: fijar `{EN_CURSO, COMPLETADA, FALLIDA}`
  como constantes; `marcar` valida y rechaza otros valores.
- **R4 (bajo, fuera de alcance)** — Concurrencia: si en el futuro un agente en
  hilo escribe mientras la web lee, SQLite sin WAL puede dar `database is
  locked`. **No se resuelve aquí** (no hay ejecución concurrente todavía); se
  anota como hallazgo para el ticket de ejecución en segundo plano.
- **R5 (bajo)** — Tentación de añadir índices, vistas o una tabla `agentes`. **No:
  una tabla, sin índices** hasta que haya volumen real (§30).
