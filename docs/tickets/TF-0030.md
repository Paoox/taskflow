## Objetivo

Cerrar el primer tramo del flujo aprobado:

    respuestas_formulario -> Discovery -> Expediente Maestro

Construir `ejecutar_discovery(codigo, cliente)` (`src/discovery/`): un punto
de entrada nuevo, independiente del Orquestador viejo, que interpreta el
formulario completo de un `codigo` (una sola vez, cuando
`siguiente_pregunta()` ya devuelve `None`) y escribe las entidades
correspondientes del modelo nuevo (`src.expediente.modelo`) mediante:

- **intérprete directo** (`src/discovery/interpretacion_directa.py`): mapeo
  determinista en Python, sin LLM, de las respuestas cerradas con
  significado completo por sí solas;
- **intérprete LLM** (`src/agentes/interprete_formulario.py` +
  `src/discovery/interpretacion_llm.py`): un agente más (`DefinicionAgente`)
  ejecutado con el runner ya existente (`ejecutar_agente`), que interpreta
  las respuestas de texto libre y devuelve JSON Lines validado antes de
  persistir.

## Contexto

Petición directa de Pao, tras dos rondas previas de análisis (brecha
Formulario→Discovery→Expediente) y diseño (Discovery nuevo separado del
Orquestador viejo, con una UI de pruebas prevista para un bloque posterior).
`src/formulario/` (árbol + validación de respuestas) y
`src/expediente/modelo.py` + sus repositorios (`Perfil`/`Requisito`/
`Restriccion`/`Dato`/...) ya existían, aprobados e implementados, pero nada
los conectaba: ningún proceso leía `respuestas_formulario` para escribir el
Expediente Maestro. Este ticket cierra exactamente esa brecha, sin tocar
ninguna de las dos piezas ya aprobadas.

## Decisiones cerradas (checkpoint de este ticket)

- **Un solo pase, no un ciclo.** A diferencia de `ejecutar_orquestador()`
  (incremental, repetible), `ejecutar_discovery()` corre una vez, completa,
  cuando el árbol ya terminó — el formulario captura todo antes de
  interpretar, así que no hace falta un modelo de ciclos.
- **Alcance de entidades: `Perfil`, `Requisito`, `Restriccion`, `Dato`.**
  `Capacidad`/`Funcionalidad`/`Relacion`/`Gap`/`Contradiccion`/
  `FeaturePropuesta`/`EstadoObservado` quedan fuera de este primer bloque:
  todas requieren relacionar entidades entre sí (`Funcionalidad`/`Relacion`/
  `Gap` viven de `relaciones`, que este ticket no construye) o deducir más
  allá de lo declarado (`Capacidad` se deduce/rara vez se declara;
  `FeaturePropuesta` es iniciativa del agente, no del usuario — generarla
  aquí violaría "nunca inventar"). Quedan para un ticket posterior cuando
  haya una etapa de consolidación/deducción.
- **Clasificación de cada pregunta del catálogo** (revisada una por una,
  `src/formulario/preguntas.py`):
  - *Genera entidad determinísticamente* (Python, sin LLM — significado
    completo por sí solo): `plataforma` (+ `plataforma_detalle`),
    `plataforma_offline`, `monetizacion`, `monetizacion_forma`.
  - *Directa sin LLM, sin persistirse como entidad*: `nombre_proyecto`
    (regla 17) — no hay una entidad "Expediente" con nombre propio en el
    modelo nuevo (`src.expediente.modelo` no la define) y este ticket no
    introduce ninguna (regla 20); se expone como metadato informativo en
    `ResultadoDiscovery.nombre_proyecto`, sin persistir.
  - *Solo control de flujo, nunca entidad* (regla 16): `perfil_usuario_continuar`,
    `funcionalidad_declarada_continuar`, `administrador_tipo_continuar`,
    `dato_recordar_detalle_continuar`.
  - *Solo "compuerta" del árbol, sin contenido propio*: `nuevo_o_existente`,
    `administracion_cantidad`, `administracion_diferencias`, `dato_recordar`
    — deciden si se abre un bloque, no declaran nada por sí mismas; no
    generan entidad ni se envían al LLM como contexto (evita tentar al
    modelo a inventar algo a partir de una compuerta vacía de contenido).
  - *Requiere interpretación LLM*: el resto de `TEXTO_LIBRE`
    (`problema_objetivo`, `referencia_proyecto_existente`,
    `objetivo_proyecto_existente`, `perfil_usuario`,
    `administrador_tipo_nombre`, `administrador_tipo_otra`,
    `funcionalidad_declarada`, `dato_recordar_detalle`,
    `restriccion_tecnica`, `restriccion_tiempo_presupuesto`,
    `restriccion_negocio`, `cierre_libre`), más la única cerrada sin
    significado autocontenido: `administrador_tipo_acciones` (solo tiene
    sentido junto al nombre de tipo de administrador que la acompaña, un
    texto libre — esa correlación es exactamente el juicio semántico que
    se delega, no se reimplementa en Python la lógica de emparejamiento que
    ya vive, deliberadamente separada, en `src/formulario/arbol.py`).
- **Contrato de trazabilidad LLM→respuesta**: cada bloque de contexto que ve
  el modelo se etiqueta `(id=<respuesta_formulario.id>)`; cada línea de
  salida debe traer `respuesta_id` igual a uno de esos `id` reales. Un
  `respuesta_id` que no aparece en el conjunto mostrado se descarta como
  información no fundamentada ("nunca inventar", regla 18) — nunca se
  persiste. Es la misma disciplina de JSON Lines tolerante línea-por-línea
  que ya usa `src.orquestador.fusion` para el agente Descubridor.
- **Confianza fijada por código, no por el modelo**: `ALTA` para toda
  propuesta del intérprete directo, `MEDIA` para toda propuesta que
  sobrevive el parseo del LLM — el parser ni siquiera lee un campo de
  confianza de la salida del modelo (regla 15).
- **Atomicidad**: determinista + LLM se combinan en una sola lista y se
  persisten dentro de un único `LoteDescubrimiento` — o se escribe el
  Expediente completo de la corrida, o no se escribe nada. Un fallo de
  persistencia marca la acción envolvente como `FALLIDA` (trazabilidad) y
  se propaga (no se silencia).
- **Trazabilidad de la corrida**: `ejecutar_discovery` registra su propia
  acción (`tipo="discovery_formulario"`, `actor="discovery"`) antes de
  invocar al agente — mismo criterio que `TIPO_ACCION_ORQUESTAR` en el
  Orquestador viejo (acción propia, distinta de la que registra
  `ejecutar_agente` para la llamada al `InterpreteFormulario`).

## Cambios realizados

- **`src/discovery/__init__.py`** — docstring del paquete; sin lógica.
- **`src/discovery/interpretacion_directa.py`** — `EntidadPropuesta`
  (dataclass interno, compartido con `interpretacion_llm.py`),
  `interpretar_directo()`: mapeo determinista de `plataforma`/
  `plataforma_detalle`/`plataforma_offline`/`monetizacion`/
  `monetizacion_forma` a `Requisito` de texto fijo, `confianza=ALTA`. Función
  pura, no recibe ningún `ClienteIA`.
- **`src/discovery/interpretacion_llm.py`** — `construir_contexto()`
  (arma el texto que verá el `InterpreteFormulario`, excluyendo lo
  determinista/control de flujo/compuertas/`nombre_proyecto`) y
  `parsear_entidades()` (JSON Lines tolerante, valida `tipo`/`respuesta_id`/
  campos requeridos por tipo, `confianza=MEDIA` fijo). Funciones puras: no
  abren conexión a BD, no llaman a ningún proveedor de IA.
- **`src/agentes/interprete_formulario.py`** — `InterpreteFormulario`
  (`DefinicionAgente`): `construir_prompt()` inserta el contexto entre
  marcas (mismo mecanismo que `Descubridor`); `parsear()` es passthrough
  puro (la interpretación real vive en `interpretacion_llm.py`, evita
  duplicar manejo de errores).
- **`src/ai/prompts/interprete_formulario.md`** — prompt nuevo, mismo
  esqueleto de 8 secciones que `descubridor.md` (tarea, zona de datos entre
  marcas, tipos de entidad permitidos, reglas anti-invención, formato JSON
  Lines, ejemplos correctos/incorrectos, "ahora genera").
- **`src/discovery/discovery.py`** — `ejecutar_discovery()`,
  `FormularioIncompleto`, `ResultadoDiscovery`, `TIPO_ACCION_DISCOVERY`.
  Combina las dos listas de `EntidadPropuesta`, las persiste en un
  `LoteDescubrimiento`, registra/marca su propia acción.
- **`docs/tickets/TF-0030.md`** — este documento.

No se modificó ningún archivo de `src/orquestador/`, `src/proyectos/`,
`src/formulario/`, `src/repositorios/` (solo se **usan**, no se editan, sus
repositorios ya existentes) ni el esquema de `src/database.py`.

Casos cubiertos:

- `interpretar_directo()`: cada rama determinista (`plataforma` directa,
  `plataforma_detalle` múltiple, `plataforma_offline`, `monetizacion` +
  `monetizacion_forma`) con su opción "negativa"/"no sé" verificada como
  "no genera nada"; controles de bucle y compuertas verificados como
  "nunca generan nada"; la propia firma de la función (sin parámetro de
  `ClienteIA`) como prueba de que nunca puede llamar al LLM.
- `construir_contexto()`/`parsear_entidades()`: texto libre llega al
  contexto con su `id`; lo determinista/control de flujo/compuertas/
  `nombre_proyecto` se excluye; JSON válido (los 4 tipos) se interpreta
  correctamente; JSON inválido, tipo no reconocido, campo faltante, o
  bloque Markdown se manejan sin lanzar; una línea rota no invalida las
  demás; `respuesta_id` fuera de lo mostrado se descarta (información
  inventada); confianza siempre `MEDIA`.
- `InterpreteFormulario`: prompt incluye instrucciones base + contexto
  entre las marcas reales (no la mención en prosa); `ticket` no se filtra a
  la zona de datos; `parsear()` es passthrough puro; integración real con
  `ejecutar_agente()` registra/completa su propia acción.
- `ejecutar_discovery()` (contra SQLite real): formulario incompleto o
  vacío lanza `FormularioIncompleto` sin registrar ninguna acción;
  formulario completo se ejecuta y devuelve `ResultadoDiscovery`; el LLM se
  llama exactamente una vez (y cero veces si no hay contexto que
  interpretar, verificado con cortocircuito simulado); las entidades
  deterministas se crean aunque el LLM no devuelva nada útil; los
  controles de bucle nunca aparecen como fuente de ninguna entidad; el
  texto libre real llega al prompt que recibe el cliente; una entidad
  válida de cada tipo (`perfil`, `requisito`, `restriccion`, `dato`) se
  persiste correctamente vía LLM; JSON ininterpretable no rompe la corrida
  y queda en `problemas`; un `respuesta_id` inventado se descarta y no deja
  rastro; `fuente_directa` correcta tanto para una entidad determinista
  como para una del LLM; confianza `ALTA`/`MEDIA` verificada de punta a
  punta; un fallo de persistencia (repositorio monkeypatcheado) revierte
  **todo** el lote de esa corrida, incluidas las entidades deterministas ya
  escritas antes dentro de la misma transacción, y dicho fallo marca la
  acción envolvente como `FALLIDA`; la tabla `expedientes` permanece vacía
  tras cualquier corrida; el módulo no importa `RepositorioExpedientes` ni
  `src.orquestador` (verificado por AST, no por texto — el propio docstring
  del módulo menciona `RepositorioExpedientes` en prosa para explicar por
  qué no se usa).
