## Objetivo

Activar la comprobación de claves foráneas de SQLite (`PRAGMA foreign_keys = ON`)
en toda conexión, para que la FK `tareas.proyecto_id → proyectos.id` —ya declarada
en el esquema— se haga cumplir a nivel de motor, como defensa en profundidad
detrás de la validación de TF-0007.

## Diagnóstico

Promoción de **BL-12**.

- **Conexiones**: se crean en un único punto, `get_connection()`
  (`src/database.py`). No hay pooling: una conexión por operación.
- **FK real** (`PRAGMA foreign_key_list(tareas)`): una sola —
  `tareas.proyecto_id → proyectos.id`, `ON UPDATE NO ACTION` / `ON DELETE NO
  ACTION`, match `NONE`. `proyectos` no tiene FK. `tareas.proyecto_id` es
  NULLable.
- **Estado por defecto**: `PRAGMA foreign_keys` = `0` (OFF). La FK declarada no se
  aplicaba.
- **`tareas.db` del repo**: `PRAGMA foreign_key_check` → 0 filas (sin huérfanos);
  1 proyecto (id=0), 1 tarea (`proyecto_id=0`).
- El pragma es **por conexión** y **no se persiste** en el archivo → debe
  ejecutarse en `get_connection()`, no en `crear_tablas()`.

## Cambios realizados

- **`src/database.py`** — `get_connection()`: se añade
  `conn.execute("PRAGMA foreign_keys = ON")` como primera sentencia tras
  `sqlite3.connect()` (fuera de cualquier transacción) + comentario. **1 línea
  efectiva.**
- **`tests/test_database.py`** — nueva clase `TestForeignKeys` (9 tests): pragma
  activo; INSERT/UPDATE raw con `proyecto_id` inexistente → `sqlite3.IntegrityError`;
  `DBManager.crear_tarea`/`actualizar_tarea` con `proyecto_id` inexistente →
  `IntegrityError` (fila sin cambios); `DELETE` de `proyectos` referenciado →
  `IntegrityError`; positivos (`proyecto_id=0`, `NULL` permitido, seed id=0,
  completar/editar válidos).
- **`docs/BACKLOG.md`** — `BL-12` → `PROMOTED` / `TF-0015`.

**Sin tocar**: esquema, la FK declarada, `ON DELETE`/`ON UPDATE`, nulabilidad de
`proyecto_id`, `app.py`, `src/modelos.py`, `src/validaciones.py`,
`src/seguridad.py`, CSRF, plantillas, `Dockerfile`, CI, requirements, ni el manejo

**Positivo (sigue funcionando):**
- `get_connection()` → `PRAGMA foreign_keys` = 1.
- `crear_tarea` / `actualizar_tarea` con `proyecto_id=0` → OK.

- `INSERT` raw en `tareas` con `proyecto_id = 999` → `sqlite3.IntegrityError: FOREIGN KEY constraint failed`.

## Riesgos

- **R1 (≈ nulo)** — `.db` preexistente con huérfanos: el pragma no falla al
  conectar ni al leer; solo un DML que viole FK falla. El repo está limpio.
- **R2 (bajo)** — Cambia la superficie de error: llamadas directas a
  `DBManager.crear_tarea`/`actualizar_tarea` con `proyecto_id` inexistente ahora
  lanzan `sqlite3.IntegrityError` en vez de crear huérfanos. Es el comportamiento
  deseado; el camino web ya lo previene por validación (TF-0007). Documentado.
- **R3 (nulo)** — Coste: una sentencia `PRAGMA` extra por conexión (µs).
- **R4 (nulo)** — `proyecto_id` NULL sigue permitido (la FK no valida hijos
  NULL); no es regresión.
- **R5 (bajo, contemplado)** — El pragma debe ir antes de cualquier transacción;
  se coloca como primera sentencia tras `connect()`.
