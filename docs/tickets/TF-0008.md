# TF-0008 — Protección CSRF de las peticiones POST

## Estado

DONE

## Tipo

SECURITY

## Prioridad

P1

## Objetivo

Proteger las peticiones POST (hoy solo `POST /crear`) frente a CSRF: toda petición
POST debe portar un token válido ligado a la sesión del navegador. Sin token o con
token inválido → **HTTP 403**, sin crear la tarea. Completa el endurecimiento de
`/crear` iniciado en TF-0007 (validación de entrada).

## Contexto

Promoción de **BL-03** (`docs/BACKLOG.md`). `POST /crear` es el único endpoint
mutador y no tenía ninguna defensa contra peticiones forjadas (`CLAUDE.md` §21).
TF-0007 resolvió la validación de entrada; faltaba CSRF.

## Cambios realizados

- **`src/seguridad.py`** (nuevo): lógica de seguridad aislada, solo biblioteca
  estándar.
  - `generar_token()` → `secrets.token_urlsafe(32)`.
  - `token_valido(enviado, esperado)` → `hmac.compare_digest` en tiempo
    constante; `False` si cualquiera está vacío.
  - `obtener_secret_key(logger=None)` → usa `TASKFLOW_SECRET_KEY`; si no está,
    devuelve una clave efímera aleatoria y emite un `warning`. **El fallback no es
    configuración válida para producción**: en despliegue la variable debe estar
    definida.
- **`app.py`**:
  - `app.secret_key = obtener_secret_key(app.logger)`.
  - `app.config["SESSION_COOKIE_SAMESITE"] = "Lax"` y `SESSION_COOKIE_HTTPONLY = True`.
  - `@app.before_request proteccion_csrf()`: asegura `session["csrf_token"]` y, en
    toda petición `POST`, exige que `request.form["csrf_token"]` coincida; si no,
    `abort(403)`.
  - `@app.context_processor inyectar_csrf_token()`: expone `csrf_token` a todas
    las plantillas.
- **`templates/formulario_tarea.html`**: `<input type="hidden" name="csrf_token"
  value="{{ csrf_token }}">` dentro del `<form>`.
- **`.env.example`**: documenta `TASKFLOW_SECRET_KEY` (obligatoria en despliegue;
  incluye cómo generarla).
- **`conftest.py`**: fija `TASKFLOW_SECRET_KEY` de test (evita el fallback
  efímero); nueva fixture `csrf_token` que extrae el token de `GET /crear`.
- **`tests/test_seguridad.py`** (nuevo): 11 tests unitarios.
- **`tests/test_app.py`**: adaptados los POST de TF-0005/TF-0007 para enviar token
  válido (fixture `csrf_token`); +6 tests específicos de CSRF.
- **`docs/BACKLOG.md`**: `BL-03` → `PROMOTED`, `Ticket = TF-0008`.

**Sin dependencias nuevas.** Sin cambios en `src/database.py`, `src/modelos.py`,
`src/validaciones.py` ni en la arquitectura.

## Decisiones y riesgos

- **CSRF manual con stdlib** (`secrets` + `hmac.compare_digest`), sin Flask-WTF —
  aprobado por Pao.
- **`src/seguridad.py`** como módulo aislado — aprobado.
- **`secret_key`** desde `TASKFLOW_SECRET_KEY`; fallback efímero + warning solo
  para desarrollo — aprobado. Documentado que en despliegue la variable es
  obligatoria.
- **`before_request` global para todo POST** — aprobado; cubre también los
  futuros endpoints POST (BL-04), que heredarán la protección sin código extra.
- **`SESSION_COOKIE_SAMESITE = "Lax"`** añadido como refuerzo — aprobado.
- **R1 (materializado y resuelto)** — Ripple en los tests existentes: todos los
  POST necesitan token. Resuelto con la fixture `csrf_token` y `_datos()` en
  `tests/test_app.py`.
- **R2 (bajo)** — Con fallback efímero, en dev las sesiones/tokens no persisten
  entre reinicios del servidor. Aceptable en dev; en Docker/despliegue se fija
  `TASKFLOW_SECRET_KEY`.
- **R3 (bajo)** — El `before_request` afecta a cualquier POST futuro; BL-04 debe
  contar con ello (sus formularios necesitarán el campo `csrf_token`).
- **R4 (bajo)** — Despliegue multi-proceso sin `TASKFLOW_SECRET_KEY` compartida →
  tokens inválidos. Cubierto documentando la variable como obligatoria.
- **Fuera de alcance (backlog, OPEN)**: BL-02, BL-04, BL-06, BL-07, BL-08, BL-09,
  BL-10, BL-11, BL-12. Ninguno tocado.
