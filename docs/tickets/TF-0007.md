# TF-0007 — Validación server-side de POST /crear

## Estado

DONE

## Tipo

SECURITY / BUG

## Prioridad

P1

## Objetivo

Validar y sanear en el servidor todos los datos de `POST /crear` para que una
entrada inválida o ausente produzca una respuesta controlada (HTTP 400 con
re-render del formulario y mensajes por campo) en lugar de un HTTP 500, y para que
no se persistan tareas con datos inválidos.

## Contexto

Promoción de **BL-01** (`docs/BACKLOG.md`). Diagnóstico sobre `app.py`
(`crear_tarea_web`, rama POST):

- `proyecto_id` ausente → `int(None)` → `TypeError` → HTTP 500.
- `proyecto_id` no numérico / vacío → `int("abc")` → `ValueError` → HTTP 500.
- `proyecto_id` numérico inexistente → inserta una tarea huérfana (SQLite no
  fuerza las FK).
- `titulo` ausente → columna `NOT NULL` → `IntegrityError` → HTTP 500.
- `titulo` vacío / `prioridad` arbitraria / `fecha_limite` con cualquier texto →
  se persisten sin validar.

## Cambios realizados

- **`src/validaciones.py`** (nuevo): función pura `validar_datos_tarea(form,
  proyecto_ids_validos) -> (datos, errores)`, sin dependencias de Flask ni de la
  base de datos. Reglas:
  - `titulo`: obligatorio, `strip`, longitud ≤ `TITULO_MAX` (200).
  - `descripcion`: opcional, `strip`, longitud ≤ `DESCRIPCION_MAX` (2000).
  - `fecha_limite`: opcional; si viene, formato `%Y-%m-%d` (`datetime.strptime`).
    Vacía o ausente → `None`.
  - `prioridad`: obligatoria, dentro de `("Alta", "Media", "Baja")`.
  - `proyecto_id`: obligatorio, entero, y presente en el conjunto de ids válidos.
    Se devuelve como `int`.
  - `datos` tiene exactamente las claves del constructor de `Tarea`.
- **`app.py`** (`crear_tarea_web`): en POST, valida con `validar_datos_tarea`
  antes de crear; si hay errores, `render_template('formulario_tarea.html',
  proyectos, errores, valores=request.form.to_dict()), 400`; si no,
  `db_manager.crear_tarea(Tarea(**datos))` y redirect. La rama GET pasa
  `errores={}` y `valores={}`. No cambia el comportamiento de GET.
- **`templates/formulario_tarea.html`**: resumen de error (`role="alert"`),
  mensaje `<p class="field-error">` bajo cada campo, y re-poblado de los valores
  enviados (`value` / contenido del `textarea` / `selected` en los `<select>`).
  Los valores reflejados van escapados por el autoescape de Jinja.
- **`tests/test_validaciones.py`** (nuevo): 34 tests unitarios de la función de
  validación.
- **`tests/test_app.py`**: +12 tests de integración del endpoint (400 en
  entradas inválidas y no persistencia; conservación de valores; 302 y
  persistencia en el caso válido, con y sin `fecha_limite`).
- **`docs/BACKLOG.md`**: `BL-01` → `PROMOTED`, `Ticket = TF-0007`; alta de
  `BL-12` (SQLite sin `PRAGMA foreign_keys = ON`, REFACTOR/DB, P3, `OPEN`) — solo
  registrado, no implementado.

**Sin cambios** en `src/database.py`, `src/modelos.py` ni en la arquitectura. Sin
dependencias nuevas.

## Decisiones y riesgos

- **Módulo de validación aislado** `src/validaciones.py` (función pura), aprobado
  por Pao. Mantiene la lógica fuera de la ruta y del template (CLAUDE.md §7) y es
  testeable sin Flask.
- **Estrategia de error**: re-render del formulario con **HTTP 400** y valores
  reenviados (no redirect+flash), aprobado por Pao.
- **Límites**: `titulo` ≤ 200, `descripcion` ≤ 2000, `prioridad` obligatoria sin
  valor por defecto, `fecha_limite` opcional `YYYY-MM-DD`.
- **`request.form.to_dict()`** colapsa multivalor; el formulario no tiene campos
  multivalor → seguro.
- **Autoescape de Jinja** activo en `.html`: los valores reflejados no abren XSS.
- **Fuera de alcance (backlog)**: BL-03 (CSRF), BL-02 (`fecha_creacion` en
  lectura), BL-04 (gestión de tareas en la UI), BL-10 (config de arranque),
  BL-12 (FK enforcement en SQLite). Ninguno se toca en TF-0007.
- **`fecha_limite`**: `datetime.strptime("%Y-%m-%d")` acepta valores sin
  cero-padding (`"2026-2-1"`); no se considera un problema para este ticket
  (sigue siendo una fecha válida). Los formatos claramente inválidos sí se
  rechazan.
