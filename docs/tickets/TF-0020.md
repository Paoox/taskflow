## Objetivo

Configuración única de `logging` (biblioteca estándar, **sin dependencias
nuevas**) con nivel por entorno y un identificador de correlación **por petición
HTTP**, más un helper reutilizable. Cubre `CLAUDE.md` §26 ("registrar errores") y
§28 (trazabilidad).

En esta etapa el **único consumidor es la app web** (un id por petición). El
runner de agentes reutilizará el mismo helper más adelante; este ticket **no**
construye trazabilidad específica de agentes.

## Contexto

Promoción de **BL-15** (origen: análisis de arquitectura para agentes,
2026-08-29).

Estado actual: no hay configuración de `logging`. La única llamada es
`app.logger.warning(...)` dentro de `obtener_secret_key()` (clave de sesión
efímera). No hay identificador de correlación ni formato consistente.

`test_seguridad.py::TestObtenerSecretKey` verifica ese warning **inyectando un
logger falso** por el parámetro `logger` de `obtener_secret_key`. Ese parámetro y
su semántica (`logger=None` → usar el logger por defecto) deben conservarse.

## Alcance

- Nuevo módulo `src/observabilidad.py`:
  - `configurar_logging(nivel)` — instala un formatter consistente (timestamp,
    nivel, nombre del logger, `correlation_id`, mensaje). **Idempotente**: llamarlo
    N veces no añade handlers duplicados (varios tests hacen `import app`).
  - Helper de correlación basado en `contextvars`: fijar / leer el
    `correlation_id` del contexto actual, con un valor de **fallback estable**
    cuando no hay contexto (no lanza).
- Integración mínima en `app.py`:
  - llamar a `configurar_logging(config.nivel_log())` en el arranque;
  - en un `before_request`, fijar un `correlation_id` por petición.
  - Sin cambiar rutas, plantillas ni respuestas.
- Nueva variable `TASKFLOW_LOG_LEVEL` (default `INFO`): accessor en
  `src/config.py` (TF-0019) y documentada en `.env.example`. Valor inválido →
  `INFO` sin excepción.
- El `warning` de `obtener_secret_key()` pasa a usar el logger central **con el
  mismo texto y la misma condición**; se mantiene el parámetro `logger=None`.

## Riesgos

- **R1 (medio)** — Interferencia con `caplog` de pytest si `configurar_logging`
  fuerza `propagate=False` o manipula el root de forma agresiva → asserts de
  logging fallan. *Mitigación:* no tocar `propagate` del root agresivamente;
  diseño compatible con `caplog`; test explícito (CA-8).
- **R2 (bajo)** — `test_seguridad.py` inyecta un `logger` falso por parámetro.
  *Mitigación:* mantener `logger=None` y su semántica; si es `None`, usar el
  logger central.
- **R3 (bajo)** — Handlers duplicados al importar `app` en varios tests.
  *Mitigación:* idempotencia (CA-1).
- **R4 (bajo)** — `contextvars` + `test_client`: el id no debe "gotear" entre
  tests; fijar y limpiar por petición.
- **R5 (bajo, de alcance)** — El `correlation_id` es, por ahora, **por petición
  HTTP**. NO construir trazado de ejecución de agentes ni propagación entre
  procesos (llega con el runner, fuera de estos cuatro tickets).

## Qué NO debe modificarse

- Rutas, plantillas, respuestas HTTP, esquema SQLite.
- Firma de `obtener_secret_key` (incluido el parámetro `logger`).
- `conftest.py`, `pytest.ini`, tests existentes.
- `Dockerfile` / CI: el `CMD` (`flask run`) no cambia; el contenedor recoge el
  logging al importar `app`.
- No añadir librerías de logging estructurado (`structlog`, `loguru`, …) — solo
  biblioteca estándar.
- No construir trazabilidad específica de agentes.

### Cambios realizados

- **`src/observabilidad.py`** (nuevo, solo `logging` / `contextvars` / `uuid`):
  - `configurar_logging(nivel="INFO")` idempotente: fija el nivel en cada llamada
    y añade el filtro y un `StreamHandler` con el formato D2 **solo si no llevan
    el atributo centinela** `_taskflow_obs`. No toca `logging.root`, no llama a
    `basicConfig()`, no toca `propagate` (queda `True`).
  - `_FiltroCorrelation` (subclase de `logging.Filter`) enganchado al **logger**:
    inyecta `record.correlation_id` en cada registro.
  - `get_correlation_id()` / `set_correlation_id(valor=None)` (→ `uuid4().hex`) /
    `reset_correlation_id(token)` sobre un `ContextVar` con `default="-"`;
    `reset` con `token=None` o token inválido cae al fallback sin lanzar.
  - `_resolver_nivel(nombre)` → constante de `logging` para
    `{CRITICAL, ERROR, WARNING, INFO, DEBUG}`; cualquier otro valor → `INFO`.
  - `obtener_logger()` → `logging.getLogger("taskflow")`.
- **`src/config.py`**: `LOG_LEVEL_ENV`, `LOG_LEVEL_POR_DEFECTO = "INFO"` y accessor
  `nivel_log()` con late binding (`os.environ` en cada llamada, sin cache).
- **`app.py`**: `configurar_logging(config.nivel_log())` en el arranque;
  `obtener_secret_key()` sin `app.logger`; `before_request`
  `asignar_correlation_id` (registrado antes de `proteccion_csrf`, sin log) que
  guarda el token en `g._correlation_token`; `teardown_request`
  `limpiar_correlation_id` que hace `reset_correlation_id(g.pop(..., None))`.
  Sin rutas nuevas ni cambios de respuesta.
- **`src/seguridad.py`**: la emisión del warning pasa de
  `if logger is not None: logger.warning(...)` a
  `(logger if logger is not None else obtener_logger()).warning(mensaje)`. Firma
  `obtener_secret_key(logger=None)`, texto y condición del warning sin cambios.
- **`.env.example`**: documenta `TASKFLOW_LOG_LEVEL` (5 niveles; valor no
  reconocido → `INFO`).
