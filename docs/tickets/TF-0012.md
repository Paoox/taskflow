# TF-0012 — Endurecimiento de la sesión en el contenedor (secret key + cookie Secure)

## Estado

NEEDS_REVIEW (implementado; verificado localmente, en Python 3.12 y en Docker.
Pendiente de confirmación externa: run real en GitHub Actions. Commit y push
pendientes de autorización de Pao).

## Tipo

SECURITY / DEVOPS

## Prioridad

P2

## Objetivo

Que el contenedor y el contrato de despliegue garanticen una `secret_key` real y
persistente, y endurecer la cookie de sesión, de modo que la protección CSRF de
TF-0008 siga siendo válida tras reinicios y entre réplicas.

## Diagnóstico

Promoción de **BL-13**. Desde TF-0008, `obtener_secret_key()` cae a una **clave
efímera** + `warning` si no hay `TASKFLOW_SECRET_KEY`. El `Dockerfile` no la
define ni la exige, así que un `docker run` normal arranca con clave efímera:
los tokens CSRF y las sesiones se invalidan en cada reinicio y no son coherentes
entre réplicas. Además `app.py` no fijaba `SESSION_COOKIE_SECURE`, así que la
cookie de sesión viaja también sobre HTTP.

**De remolque (BL-11 ampliado):** `.dockerignore` no excluía `conftest.py` ni
`docs/`, que entraban en la imagen vía `COPY . .`.

## Cambios realizados

- **`src/seguridad.py`**:
  - `es_produccion()` → `True` solo si `TASKFLOW_ENV` vale exactamente
    `production` (tras `strip().lower()`).
  - `cookie_secure_activada()` → lee `TASKFLOW_COOKIE_SECURE`
    (`1|true|yes|on` → `True`; por defecto `False`).
  - `obtener_secret_key()` gana **fail-fast**: si no hay `TASKFLOW_SECRET_KEY` y
    `es_produccion()`, lanza `RuntimeError` (el proceso no arranca). Sin la señal
    de producción, mantiene el fallback efímero + `warning` (comportamiento de
    desarrollo intacto).
- **`app.py`**:
  - importa también `cookie_secure_activada`.
  - `app.config["SESSION_COOKIE_SECURE"] = cookie_secure_activada()`.
  - comentario actualizado (TF-0008 / TF-0012).
- **`Dockerfile`**: bloque de comentario con el **contrato de despliegue** (la
  imagen sigue **neutral por defecto**; producción declara explícitamente
  `TASKFLOW_ENV=production`, `TASKFLOW_SECRET_KEY=<clave real>`,
  `TASKFLOW_COOKIE_SECURE=1`). **No** se añade `ENV TASKFLOW_ENV=production`.
- **`.env.example`**: documenta `TASKFLOW_ENV` y `TASKFLOW_COOKIE_SECURE`;
  aclara el fail-fast en producción para `TASKFLOW_SECRET_KEY`.
- **`.dockerignore`**: excluye también `conftest.py` y `docs/` (BL-11 ampliado).
- **`tests/test_seguridad.py`**: +12 tests (`TestFailFastProduccion`,
  `TestCookieSecure`).
- **`tests/test_app.py`**: +1 test — `SESSION_COOKIE_SECURE` es `False` por
  defecto en el entorno de test y el flujo CSRF sigue en 302.
- **`docs/BACKLOG.md`**: `BL-13` → `PROMOTED`/`TF-0012`; `BL-11` → `PROMOTED`/
  `TF-0012` con texto ampliado.

**Cambio funcional estrictamente limitado** a: clave de sesión, cookie `Secure`,
documentación, tests y configuración del contenedor. Sin tocar rutas, modelos,
esquema, `src/database.py`, `src/validaciones.py` ni plantillas. Sin dependencias
nuevas. Sin `docker-compose`. Sin almacén de sesiones/tokens.

## Riesgos

- **R1 (mitigado)** — `SESSION_COOKIE_SECURE=True` sobre HTTP impediría enviar la
  cookie (todos los POST → 403). Mitigación aplicada: **default `False`**; test
  explícito de que con `False` el flujo CSRF sigue OK (escenario D2 + `test_app`).
- **R2 (decisión de Pao aplicada)** — El `Dockerfile` **no** fuerza
  `TASKFLOW_ENV=production`; queda neutral. Producción lo declara explícitamente.
- **R3 (bajo)** — Se modifican `app.py` y `src/seguridad.py`; es el núcleo del
  ticket, cubierto por 12 tests nuevos + CI.
- **R4 (bajo)** — El `test_client` de Flask no ejercita el caso `SECURE=on` sobre
  HTTPS; se verifica vía Docker (`Set-Cookie ... Secure`) y a nivel de config.
- **R5 (nulo)** — No toca lógica de negocio ni esquema de datos.
